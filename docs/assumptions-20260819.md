# 合意済み前提（2026-08-19）

`arch-requirements` スキルの前提確認プロセスで合意した内容。設計判断の根拠はすべてこれに依存する。

| # | 前提 | 状態 |
|---|------|------|
| 1 | 本番環境は **Talos Linux の単一ノード Kubernetes クラスタ**（クラスタは別リポジトリ `thin-k8s` が管理する。dev/prod の環境分割ではない）。`replicas: 1` から開始するが、**HPA による水平 Pod スケールが実際に機能すること**を要件に含める | 合意（2026-09-02 更新。当初は k3s / k3d 前提） |
| 2 | Go 側 API は自作コンテンツを JSON で返す程度。**DB は持たない**。データはリポジトリに同梱する | 合意 |
| 3 | k8s 運用そのものがポートフォリオの一部。ただし複雑さの誇示ではなく、**シンプルで説明できること**を優先する | 合意 |
| 4 | Cloudflare Tunnel は **クラスタ内 Pod**（cloudflared）として動かす。ホストのプロセスにはしない。**2026-09-02 追記: 判断自体は生きているが、cloudflared の所在は `thin-k8s` の core 層へ移った**（portfolio は Pod を持たない） | 合意 |
| 5 | 反映経路は **GitHub Actions + ArgoCD による GitOps**。手動 `kubectl apply` は運用手段に含めない。コンテンツ自体はリポジトリ同梱のままで、動的更新（CMS 的な仕組み）は不要 | 合意（訂正済） |
| 6 | 開発は Docker / devcontainer 内で完結させる。ホストに Go / bun を直接入れる運用は取らない | 合意 |

## 前提から外れた場合の再検討トリガ

- **2 が崩れる（DB を持つ）** → ステートレス性が失われ、HPA の前提と単一バイナリ構成の両方を再検討する
- **3 が崩れる（k8s は手段にすぎない）** → Cloudflare Pages + Workers が最短になり、VM 運用ごと不要になる
- **5 が崩れる（動的更新が必要）** → コンテンツを静的埋め込みから外し、ConfigMap か外部ストレージへ移す
